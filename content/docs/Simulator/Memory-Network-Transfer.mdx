### Data Path Selection

For local transfers, the `DataPathManager` checks configured memory-pair mappings:

- If `(src_mem_id, dst_mem_id)` matches a configured dedicated pair, the transfer uses a `local_dedicated_data_path`
- Otherwise the transfer falls back to `intra_core_bus`

Global load/store and inter-core send/receive always use `inter_core_bus`. Dedicated data paths are defined in `transfer_unit_config.local_dedicated_data_path_list`.

## Transfer Runtime Stages

Each transfer instruction passes through three stages inside the `TransferUnit`.

<Accordions>
<Accordion title="Local Transfer Runtime">

Local transfers use `LocalTransferDataPath` with batch splitting. Each batch transfers up to `max(src_read_width, dst_write_width)` bytes, using the wider port width as batch size. The total number of batches is `ceil(size_byte / batch_max_data_size_byte)`.

<div className="fd-steps [&_h4]:fd-step [&_p]:my-1">

#### Issue [!toc]
Create per-batch payloads from the full transfer request

#### Read [!toc]
Read the local source memory range for each batch

#### Write [!toc]
Write the destination range, release resources on the last batch, and mark the instruction as finished

</div>

Pipelining activates when `transfer_unit_config.pipeline = true` and `src_mem_id != dst_mem_id`.

<Callout type="warn" title="Scalar Memory Timing">
Scalar memory accesses use a separate timing path from vector and transfer operations. Non-scalar requests wait for the modeled access delay inside the memory module, while scalar-initiated accesses bypass this wait. Reported latency for scalar load/store may differ from vector or transfer operations targeting the same memory.
</Callout>

</Accordion>
<Accordion title="Global and Inter-Core Runtime">

Global and inter-core transfers use `GlobalTransferDataPath`. The behavior varies by transfer type.

| Type | Read Stage | Write Stage |
| --- | --- | --- |
| `global_load` | Load from global memory through NoC | Write to local memory |
| `global_store` | Read from local memory | Store to global memory through NoC |
| `send` | Read local payload (after handshake) | Send data to destination core |
| `receive` | Wait for remote data (after handshake) | Write received data to local memory |

### SEND/RECV Handshake [!toc]

Inter-core communication follows an explicit handshake protocol.

<div className="fd-steps [&_h4]:fd-step [&_p]:my-1">

#### Sender Ready [!toc]
Sender announces readiness (`sender_ready`)

#### Receiver Ready [!toc]
Receiver confirms readiness (`receiver_ready`)

#### Data Transfer [!toc]
Sender transmits data (`send_data`)

#### Complete [!toc]
Receiver unblocks and completes

</div>

The `transfer_id_tag` field pairs each sender with its receiver. A mismatch throws a runtime exception.

</Accordion>

The simulator supports two NoC transfer modes.

| Mode | Behavior | Used By |
| --- | --- | --- |
| `transport` | Models request + response delay | Global load/store |
| `only_send` | Models one-way send delay | Send/recv, sync notifications |

## Synchronization Through Transfer Path

`TAG` and `WAIT` are executed in the `TransferUnit` runtime path. For the full ISA-level semantics, see [Execution and Resource Model](/docs/Simulator/Execution-Model).

- `TAG` stores `sync_id` and attaches it to the next `global_store`
- A tagged `global_store` triggers `notify_write_complete(sync_id)` to global memory
- `WAIT` sends `wait_for_writes(sync_id, expected_writes)` and blocks until `sync_complete`
- Consecutive `TAG` without an intervening tagged store is treated as a fatal invalid sequence

<Callout type="info" title="Control Path Split">
`TAG` and `WAIT` are control opcodes at decode level, but their runtime behavior is implemented by the transfer/network/global-memory path.
For decode and issue details, see [Execution and Resource Model](/docs/Simulator/Execution-Model).
</Callout>
